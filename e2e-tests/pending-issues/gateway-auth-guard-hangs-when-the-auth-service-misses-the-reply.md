# The gateway's auth guard hangs an HTTP request forever when the auth service never replies, freezing the UI

**Status:** gateway side fixed (`Users.getUserByToken` waits at most 30 s and `sendMessageWithTimeout` clears its timer); the frontend side is fixed too (`ProfileService.pushSetProfile` / `restoreProfile` end with a toast after 30 s, so the spinner is released); the other `Users` lookups behind guards and handlers still have no deadline and are still open — infra robustness bug. First seen 31 Oct as one transient wizard hit; on 10 Nov 2026 the same class froze two more UI pages (user management, policy editor) in the 02 suite - see the observations below
**Component:** `common/src/mq/nats-service.ts` (`sendMessage`) + `api-gateway/src/auth/auth-guard.ts` + `api-gateway/src/helpers/users.ts` (`Users.getUserByToken`, `Users.generateNewAccessToken`, and the rest of the `Users` lookups); the frozen UI is whatever page's content fetches dedupe onto the stuck request
**Severity:** medium - one transient hit in ~40 wizard runs on 31 Oct, plus two full-page freezes in one day of 02-suite runs on 10 Nov; the consequence is a full-screen spinner that never resolves (no error, no timeout, no way out) and the affected user can only reload (and a reload is only a lottery, not a fix, when the stored tokens are the problem)
**Found by:** `e2e-tests/cypress/e2e/ui-tests/specs/00_account_registration/` run of 31 Oct 2026: after the USER wizard's `Confirm` click, the app fired `PUT /api/v1/profiles/push/:user` and the page froze on a spinner. The attached `[proxy]` request logger (`frontend/proxy.hostdocker.js`) shows the request went out and no `<-` status line ever came back. An identical `PUT /profiles/push` repro via `curl` 30 minutes later answered `202 in 24ms`, so the miss was transient, not an outage.

## Symptom

- The user finishes the registration wizard and clicks **Confirm**.
- The app shows a full-screen loading spinner and never shows anything again: no 202, no error toast, no navigation.
- In the ng-serve proxy log the request is a one-way trip: `-> PUT /api/v1/profiles/push/:user` with no matching `<- <status>` line, ever. The gateway accepted the request and then holds it.

## Where it comes from

1. **Frontend:** `createDID()` (`user-profile.component.ts`) sets `loading = true` and `headerProps.setLoading(true)` (the full-screen spinner), then calls `profileService.pushSetProfile(profile)` — a plain `http.put(...)` with **no HttpClient timeout**, and the error callback only fires for responses that actually arrive. A request that never answers produces no error and no spinner relief.
2. **Gateway:** `PUT /profiles/push/:username` (`api-gateway/src/api/service/profile.ts`) is decorated `@Auth(Permissions.PROFILES_USER_UPDATE)`, which stacks `AuthGuard` in front of the handler. `AuthGuard.canActivate` does `request.user = await this.users.getUserByToken(token)` — **before** the handler can run, and its `catch` maps a *rejected* lookup to 401.
3. **The unbounded wait:** `Users.getUserByToken` (`api-gateway/src/helpers/users.ts`) is `NatsService.sendMessage(AuthEvents.GET_USER_BY_TOKEN, { token })`. `sendMessage` (`common/src/mq/nats-service.ts`) resolves its promise only when the auth service publishes a reply on the gateway's `replySubject` inbox — there is **no timeout** on that wait (`Users.getUserByToken` has been bounded to 30 s since 31 Oct, the other lookups still wait forever). If the reply never arrives (auth service busy or restarting, NATS reply lost, reply routed to a dead or stale inbox), the promise stays pending forever, the guard's `await` never returns, and the `catch` cannot help because nothing rejects.

So a single dropped reply from the auth service turns one HTTP request into a request that is open until the browser gives up, and the wizard UI — which blocks on exactly that request — into a dead end. The whole `Users` helper (dozens of NATS lookups behind guards and handlers: `currentUser`, `permission`, `registerNewUser`, `generateNewAccessToken`, …) is exposed to the same mode; any authenticated route can hang the same way.

`NatsService` already ships the fix as a primitive — `sendMessageWithTimeout(subject, timeout, data)` (a `Promise.race` that rejects with `REQUEST_TIMEOUT` and cleans up the callback) — it is just not used on this path.

Two of the exposed lookups were confirmed no-deadline in the 10 Nov freezes:

- `Users.generateNewAccessToken` is a plain `sendMessage` — the `POST /accounts/access-token` leg of the 401 recovery. `Users.getUserByToken` (the 30 s-bounded one, fixed after 31 Oct) is the only `Users` lookup with a deadline.
- The auth-service side of that leg does reply on a failure: `NatsService.getMessages` (`common/src/mq/nats-service.ts`) catches any throw of a handler and replies with a 500 error (since `12b48fe7d`, 8 Sep 2026; re-checked on 11 Nov 2026), so a stale or undecryptable refresh token produces an error reply, not silence. The `JsonWebTokenError` lines (`jwt must be provided`, `jwt malformed`) in the auth-service log come from that catch (`nats-service.js:399`): malformed tokens do reach verification in this stack, and they are answered. (The `GET_USER_BY_TOKEN` handler also wraps everything in a try/catch that replies `MessageError`, so rejected lookups 401 cleanly.) A hang therefore needs a reply that is lost in transit or an auth service that is busy or down, not a handler that throws; the hang was not reproduced on demand on 11 Nov 2026 (transient).

### 10 Nov 2026 observations (02 suite, one day of runs)

All boots in these runs fired the app's workspace bootstrap; the access token TTL is 30 s and `AuthStateService` proactively refreshes on a 29 s timer, so every boot whose token lapsed (a timer that fires late in the backgrounded headless browser included) hit 401s. The gateway log for the day shows exactly-4 `Unauthorized request` bursts at 02:50:29, 02:55:38, 03:34:15, 03:36:25, 04:07:23, 04:10:32, 04:10:41, 04:14:01, 05:30:30 and 05:37:07.

- **Policy editor (iREC5 spec, ~02:53:45-02:55:5x):** `importPolicyFromFile` ended on `waitForPageReady('div.view-segment', 4)` and lost all four boots. The import itself had run (worker task activity 02:54:18-20) and the segment marker is genuinely absent until the editor data lands (the template gates it on `isModuleValid`), so this was not a marker problem: each reloaded boot hung its bootstrap inside the 401-refresh window, the burst at 02:55:38 sits in the middle of the retry window. The frontend amplifier: `AuthInterceptor` dedupes every 401 onto one shared in-flight `refresh$` (shareReplay, no timeout, and `refreshAndRetry` has no error path) — a refresh POST that never settles leaves **every** deduped request pending, and each page's `loading` state (which only flips on a response, in either direction) stays true forever.
- **User management (CDM spec, 05:30-05:37):** the second visit to `/user-management` rendered, then froze on the component's `div.loading` overlay. Every fetch that completed answered 200; the ones that never came back are the ones `loading` waits on. The 05:37:07 burst (exactly 4) lands at the failure moment. Same amplifier: `forkJoin(profile, roles)`/`getUsers` dedupe onto the stuck refresh.
- **Login page:** the trailing-slash `POST /accounts/login/` 401 clusters in the day's proxy log are the suite's own HBAR balance snapshot (`snapshotHbarBalances` in `cypress.config.js`, wired to `before:run`/`after:run`): it logs in 12 accounts node-side, four of which are not registered in this workspace, so each snapshot is a 12-request burst (8×200 + 4×401). That is node-side accounting, not app behaviour - and it was initially misread as "the login endpoint 401s on good credentials, transiently". The browser logins (no trailing slash) all answered 200 (65 of them in the day's log, zero 401s), so there is no endpoint flake to track here. The login-side failures that actually happened that day were test-side, in `homePage.login` (see Test impact): the first hardened version of its recovery compounded into a storm (a self-perpetuating poll re-fires across `cy.reload()`), and a leaked `ensureAccount` login then ran a second concurrent `login()` chain under the spec's next login. Both are fixed in the page object.
- **Background noise, never blocking:** every app boot also fires `GET /demo/registered-users`, which never gets a `<-` line in the whole day's proxy log (~38 times). Nobody blocks on it, so it freezes nothing - but it is the same no-reply class and a future consumer of that route would inherit the hang.

## Suggested fix

- Use `sendMessageWithTimeout` (a few seconds) for the token/user lookups behind `AuthGuard` at minimum; the guard already maps *any* throw to `401 Unauthorized`, so a timeout maps cleanly to the one behaviour the frontend's auth interceptor is already built to handle (refresh + retry). `Users.getUserByToken` has this since 31 Oct; `Users.generateNewAccessToken` (the refresh leg) and the rest of the `Users` lookups still do not.
- Better: bound the wait centrally — a `Promise.race` in `canActivate`, or a Nest interceptor/HTTP deadline — so no guard or handler can hold a request open indefinitely.
- Frontend hardening: done for the wizard push (30 s timeout and a toast on `pushSetProfile` and `restoreProfile`). The remaining exposure is the shared `refresh$`: a refresh that never settles freezes every deduped request - a `timeout(...)` on `updateAccessToken` inside the interceptor would turn the permanent spinner into a logged-out redirect.
- Frontend hardening (separate): the 29 s proactive refresh races the 30 s token TTL by one second; in a throttled (backgrounded/headless) tab the interval can fire late and the next boot 401s. A margin there (refresh at 20-25 s) would shrink the 401 window the hangs need.

Note: this is a **different** bug from `registration-wizard-stalls-when-the-task-result-is-lost.md` (there the 202 *was* delivered and the task result was lost client-side). Here the 202 is never sent at all — the request dies inside the auth guard.

## Test impact

- The 00 suite now survives both stall modes: `generateHederaAccount()` covers the Generate race, and `waitForTaskNavigationOrRecover(runWizard)` covers this one — after the `Confirm` click it polls for the `/task/...` navigation for 60s; on timeout it reloads, waits for the app to settle, redoes the wizard tail once, and fails loudly if it still does not navigate.
- The SR Connect flow (`hederaSRRegistration` → same `push` call) has the same exposure. It has passed three consecutive full runs, so it does not get the reload-redo recovery in the tests — its exposure is covered by this entry as product-side work.
- The 10 Nov 02-suite freezes were met with the same bounded-recovery idiom where the page could express it: `userManagementPage` gates on the loading overlay being *gone* (`waitForPageSettled` - the content it covers is always in the DOM, so a presence marker passes while the page is frozen), `tokensPage` budgets the post-grant row re-appearance with the reload ladder, and `homePage.login` gates every form interaction on the live document and recovers a never-settling login POST by wiping the stored tokens and re-entering from a fresh boot (a 401 instead gets one plain re-submit). A generation counter makes that recovery single-shot - a self-perpetuating poll continuation queued before the recovery's `cy.reload()` would otherwise survive it and re-fire the recovery, which compounded into a reload-and-login storm (the v3 runs died on it) - and the method returns its chain so a caller inside a `.then()` callback cannot leak a second concurrent `login()` chain (`ensureAccount` did exactly that: its login ran under the spec's next login and the two chains tore each other's form and tokens apart; the v4 runs died on it). `logOut()` also wipes the refresh token defensively, because a sign-out path that leaves it would let the app re-bootstrap the previous user on the next reload, unmounting the form the next login is about to type into. `pageReadiness.js`'s ladder (`withReloadBudget`) is the shared primitive. These recoveries only spend time when the hang actually happens; the product-side gaps above are what they buy time against.
- Diagnostic tooling: the `[proxy]` request logger in `frontend/proxy.hostdocker.js` is how the hangs are spotted (a `->` line with no `<-` line). Any future e2e failure that shows a fired request with no response is most likely this mode, whatever the route.
